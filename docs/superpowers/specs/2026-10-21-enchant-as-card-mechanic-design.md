# 附魔改为卡牌机制 设计

日期：2026-10-21

## 背景与目的

现在的附魔是引擎里单独的一套逻辑：靠卡牌 id 后缀区分（`*` = 训练指南的成长附魔，`^` = 固有附魔，`+` = 锻造），战斗里的 `isEnchanted(id)` / `isInnate(id)` 直接决定行为，`enchant.ts` 里有大段按后缀拆 id 的代码。

目的：让附魔不再是特殊概念。**附魔 = 给一张牌补上一个卡牌自己的机制**，写法和卡牌构建器的链式调用一致（`.retain()`、`.innate()`、`.grow(1)`），和卡组编辑器里"把消耗改成不消耗"是同一类操作。引擎只认卡牌的机制字段；"附魔"只在界面呈现和牌组存储上留下一个名字。新增一种附魔，只需登记名字和一段链式调用。

## 目标

- 每个附魔有名字和一段对卡牌的链式调用。首批三个：
  - 增量（原训练指南的成长附魔）：`.grow(1)`，每打出一次，卡面数值 +1（X 牌是 X 加成 +1）。
  - 固有：`.innate()`，每场战斗第一回合必定抽上手。不改费用。
  - 保留：`.retain()`，回合结束留在手牌（`Card.retain()` 已存在）。
- 战斗引擎不再出现"附魔"概念：成长看牌的 `grow` 字段，固有看 `innate` 字段，保留看 `retain` 字段。
- 界面照常呈现附魔：卡面显示宝石标识和附魔名，依据是牌组里记的附魔名，**不是**从机制字段反推。所以"本来自带保留的牌"没有宝石，"被附魔成保留的牌"有宝石。
- 遗物 / 事件选牌时，可选范围按卡牌自己的机制字段自动算出，不另写规则。

## 非目标

- 不新增获得附魔的途径（遗物、事件）。训练指南改为附「增量」；王国公章改为附「固有」；「保留」只先登记，是否配遗物或事件另议。
- 不改锻造（`+`）和进化（`~N`）的存储方式，只保证它们与新附魔字段共存。
- 不做一张牌多个附魔，也不做替换附魔。

## 反目标（出现就算失败）

- 引擎或战斗代码里重新出现按附魔名分支的逻辑，而不是看机制字段。
- 已经自带某机制的牌仍然能被附魔成同一个机制（例如自带保留的牌能选「保留」）。
- 旧存档里的附魔牌读档后丢失附魔，或变成两个附魔。

## 已确定的规则

1. 一张牌最多一个附魔（用户明确要求）。因此已经带有附魔的牌，不能再被附魔，也不做替换。
2. 牌已有某机制时不能附魔成该机制。可选性由机制字段判断：增量要求没有 `grow`，固有要求没有 `innate`，保留要求没有 `retain`。
3. 附魔是数据：名字 + 链式调用。牌组里每张牌只记一个附魔名。
4. 战斗开始时，带附魔的牌先执行其链式调用，变成机制不同的牌；之后与普通牌无异。
5. 增量的计数（每张牌各自打了几次）仍存在战斗实例里，每张牌互相独立；附魔只负责打开 `grow` 机制。

## 存储与兼容

- 牌组仍是字符串 id 数组。用单一后缀 `@附魔名` 取代 `*` 和 `^`，例如 `strike@grow`、`strike+@innate`。规范顺序：基础 id、可选 `+`、可选 `@名`、可选 `~N`、战斗实例 `#下标`。
- 旧存档读档时把 `*` 转成 `@grow`、`^` 转成 `@innate`。旧版允许两者叠加；若同时存在，保留 `@grow` 并去掉固有（这是我的取舍，因为新规则只允许一个）。
- 进化（`evolvedId`）保留升级和附魔标记，丢掉进度，行为不变。

## 界面

- 卡面宝石标识由牌组里记的附魔名决定，鼠标悬停显示附魔名（增量 / 固有 / 保留）。
- 增量原有的卡面文字行为不变；固有的卡面开头仍写「固有。」；保留沿用 `Card` 已有的「保留，」前缀。
- 选牌界面（遗物 / 事件）只列出可附魔的牌。

## 我替你定的几处（请核对）

这些是我自己的决定，不是你说过的：

- **固有不再让费用变 0（用户明确更正）**：这是对现有行为的改动，现在固有牌费用为 0，需要同步去掉；王国公章的描述文字「费用为 0」也要改成只写第一回合必抽上手。已持有固有牌的旧存档，读档后费用恢复为牌的原价。
- **附魔和锻造的先后**：先按锻造后的牌面算，再执行附魔的链式调用。这与现有行为一致（先锻造、再标记附魔），所以增量按锻造后的数字 +1。
- **可附魔判断只看牌当前的样子（用户确认）**：传说斗篷未升级时没有保留，可以被附魔成保留；之后锻造，升级版自己也带保留，两者重复，无事发生，不需要处理。
- **`retainGrow` 牌算已有保留**：它本身带保留，所以不能再被附魔成「保留」。
- **旧存档同时有 `*` 和 `^`**：只保留增量，去掉固有（见"存储与兼容"）。

## 留给实现者决定

- 链式调用如何落到引擎使用的卡牌定义上：当前引擎拿到的是已构建好的定义，而不是 `Card` 构建器。可以让卡池保留构建器、按需生成附魔版本；也可以提供与构建器同名的定义层辅助函数。硬性要求只有一条：**登记一个附魔时，写法是链式调用的形式**。
- `.grow(1)` 与现有 `growCard` 的数值累加逻辑如何对接（现有逻辑按文字里的数字加 1，需保持卡面与数值同步）。
- 附魔名在代码里的标识符（`grow` / `innate` / `retain` 是我的暂定命名）。
- 现有测试里依赖 `*`、`^` 后缀的用例的迁移方式。

## 涉及范围（现状摘要）

- 引擎：`src/engine/enchant.ts`（后缀拆解、`growCard`、`resolveCards`）、`battle.ts`（固有开局抽牌、打出后成长）、`relics.ts`（训练指南、王国公章选牌）、`types.ts`（`enchanted` / `innate` 字段）。
- 界面：`CardView.vue`（宝石标识）、`RelicReveal.vue`、`useSfxEvents.ts`（"新附魔"判断）、`sfxScenes.ts`。
- 数据：`items.ts` 里训练指南的描述文字。
